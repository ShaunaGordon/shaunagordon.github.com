[Opal](https://opallauncher.com/)!

I can finally talk about it! This has been a project I've been working on at Genome Studios, and have been excited about for months, especially since in the past few, I kept seeing people in the O3DE community expressing the desire for the very things Opal provides.

For anyone coming from Unity or Unreal, Opal should be instantly familiar as a tool to manage engine versions, gems, and projects. It's a tool O3DE has been sorely lacking, due to how coupled its internal project manager is to the engine version, itself. Opal decouples project management from the engine itself, vastly expanding the manager's potential capabilities.

## Why Build Opal?

O3DE is a great engine, with a great community, but there are a few recurring bits of feedback we kept seeing, and issues we encountered ourselves:

- There's no gem marketplace. You have to know about gems and how to add them to your version of O3DE, then manage them yourself.
- Getting prerequisites for O3DE can sometimes be a challenge, and not-infrequently hinders newbies from getting up and running.
- On Windows, installing sometimes fails entirely, due to Python not installing. (To the maintainers' credit, they put in a lot of work playing Whack-A-Mole with all the myriad reasons this happens, and managed to get like 95% of the causes, with the last ones being the most difficult to nail down.)
- Installing multiple versions of the engine is possible, but cumbersome and is very much the "swimming against the current" path.
- A lot of O3DE's features are buried behind scripts, CLI commands, or just in the sheer number of features in general.

So, we set out to solve most of these, and with Opal, we've done so for all but the marketplace bit (that has its own mountain of logistics to deal with, but we do make it easier to add collections of gems).

### Why A Third Party App?

The next obvious question is, of course, why did we make our own app, instead of "just" fixing the O3DE project manager, itself? 

There were a few reasons for that, but the biggest is because in order to manage multiple versions of the engine, the project manager needed to be decoupled from the engine itself. Right now, each version of O3DE ships with its own copy of its project manager. Creating projects in a given project manager defaults that project to that version of the engine, and you can't change that until after the project is created. Then, there's the recurring issue of the prerequisites. Without a self-contained application to manage the prerequisites, you're kind of dead in the water.

Making our own app also gives us full control over its development direction and all decisions with it, and lets us do things the O3DE project/foundation is reticent to do, such as interfacing with third-party gem repositories that require authentication.

## So You Want To Build A Launcher...

Desktop applications are their own beast when it comes to choosing a tech stack. In the web world, it's pretty easy -- pick your favorite language and database, decide whether you're going to use a JavaScript UI framework, and fire it up in a Docker container. The rest of the details don't really matter, because the web uses a standard set of protocols that are shared across all language ecosystems, so it really doesn't matter all that much what developer tools a person uses, it all results in essentially the same base user experience.

On desktop, though? The tech stack decision can greatly limit what systems your project works on, how good it looks, even how well it functions. Swift UI makes for beautiful applications...on Mac. The Browser Company spent ages porting it, just to have their Arc browser work on Windows. Likewise, Windows Presentation Foundation (WPF) is a pretty nice (IMO) declarative UI framework...for Windows. It took several years after the open-sourcing of .NET itself for Microsoft to open-source WPF, and it *still* only officially supports Windows, requiring resorting to third-party (typically paid) solutions. Java, of course, famous for its "write once, run anywhere" goal, naturally has several options, but tends to be notoriously bloated, not to mention the licensing questions with Java, itself. For a shop that's not already using it, it just doesn't make a lot of sense.

So...we needed something cross-platform, that was also easy to maintain in the long run. One of the obvious contenders would be Qt and C++. They're the quintessential native, cross-platform pairing, powers a very large portion of the open source world, and is even with O3DE itself uses. The other obvious route was Electron with a JavaScript/HTML UI framework of choice. Such a stack runs such popular tools as VS Code, Discord, and Slack.

### And The Winner Is...

We needed to balance speed of development, maintenance burden, onboarding new engineers, and application footprint. This ruled out any kind of stack that would require porting or maintaining any of the myriad cross-platform pitfalls. 

Because we opted to make Opal closed-source, at least for the time being, that also complicated the prospect of using Qt, which is GPL licensed, and not all parts are necessarily dual-licensed under the more permissive LGPL, and would therefore require additional vigilance on our part. Might we have been okay? Maybe, and while I am a rather well-informed engineer, I'm still not a lawyer, and I'm not about to risk legal hot water for picking the wrong license version or grabbing a control that's only GPL or whatever.

That leaves us with Electron...except Electron is *heavy*. Anyone who has ever run any of the aforementioned applications knows they often consume a gig of RAM or more when adding up all their processes, even when idle. It's also Chromium-based, and so has the same 6-week major update cadence as Chromium, as well as many of its issues. That means it fails our maintenance burden and footprint goals. (I've updated an Electron application that fell behind before, I'll pass on doing that again.)

Thankfully, because of previous forays I've taken into the world of Electron alternatives, I knew about [Tauri](https://tauri.app/). The project's focus on stability and security gave us a solid foundation from which to work, and its small base footprint means all of Opal's processes take a combined less than 500MB of RAM, freeing half a gig or more for using O3DE. It also uses Semantic Versioning, so we can easily keep it up to date, without having to worry about things breaking randomly. The biggest downside is that it's Rust-base, but Rust has great developer ergonomics and tooling, so between that and Agent assistance, I didn't see it as much of a barrier.

That takes care of under the hood. What about UI? Going with a web stack is a requirement of a solution like Tauri, and while Tauri does support some Rust frameworks, they are still in pretty early development even now (and moreso almost a year ago, when we were making these decisions). So, I opted for a JS/HTML framework. I'm personally partial to Vue, having used both it and React, and dabbled in Svelt, so that's what I opted for. The clear delineation between HTML templates and JavaScript logic also helped to decide. I'm not really a fan of shoving HTML templates into JavaScript the way React does it. Besides, going with Vue also avoided all the drama in the React community over [insert feature from recent version here]. (To be fair, that's not to say the Vue community is completely drama-free, but its structure does seem to make the particular kind of drama found in the React world less likely.)

## Hey Claude...

I've written about my forays into [spec-driven development](/tags/sdd) a few times now. Opal has kind of been my flagship project on developing my own SDD workflow, with the underlying question of "what does it really take to make an Agentic development workflow that produces code I'm not ashamed of putting my name on?" I take pride in the code I ship to production, so while I do have some toy projects that were done with looser reigns on the Agent, I wanted to hold Opal as a whole to a higher standard (and didn't want to drive myself batty with what amounts to plate-juggling of fragile features). That meant holding the Amnesiac Intern to the same standard I hold fellow human engineers, myself included.

This means I started the project with a Constitution that outlined the code standards for the project. For the most part, the rules are pretty typical of good software engineering, as well as some project-specific things, and my own preferences:

- follow SOLID principles
- follow best practices for Vue/Tauri/Rust
- Vue components must have Storybook stories associated with them
- use Single File Components for all Vue components
- business logic must have (useful) tests
- use test-driven development practices
- O3DE's manifests are the source of truth
- limiting the number of CSS classes on an element, and instead favoring creating semantic CSS classes that bundle those utility classes together (the project uses Tailwind as one of its design foundations, which can get super class-happy if not kept on a tight leash)
- all foreground/background color combinations must meet or exceed WCAG 2.2 Level AA for contrast ratio for both text and component boundaries
- offload time-consuming tasks to background processes, using Tauri's threading feature to manage threads

### Where To Put Specs?

I've written about this already in my SDD posts, but this is where I hammered out the details I landed on.

In the very early stages of the project, I put the specs into a `specs` folder. I needed *somewhere* to dump all the initial tasks that come with starting a brand new project that didn't at the time seem to warrant tickets for. I also quickly found that I didn't really like them there.

Having specs in the repo gives the agent another collection of documents that may or may not be relevant for context, holds onto what are ultimately transient bits of information, and means yet another place to look for the record of what work was done. When there's already a place for that information to live that gracefully handles the transient nature, is still searchable, and automatically enumerates things without the risk of collisions, it seems ludicrous to reinvent the wheel. It wasn't long before I created my Gitlab-based workflow.

### How to Keep Claude on the Rails?

LLM-based tools are notorious for going off the rails and down some crazy rabbit holes when left to their own devices. So, one of the immediate tooling issues was how to address that issue and prevent it from happening.

Over the course of the project, I developed a set of workflow skills, a process, and settings to control what Claude could do and how. After I had it working for a few months, and found myself copying a bunch of things to side projects, I turned those skills and settings into plugins, then created an internal tool that bootstraps projects by installing the plugins and adding the selected foundational documents.

Specs are written by hand, and changes are reviewed manually. [I've detailed that process and why in another post,](/2026/08/27/more-adventures-in-spec-driven-development/) so I won't belabor the matter here. In short, though, it keeps the specs narrowly-focused, and ensures that only the specced changes are what's being made, and the code is to an acceptable standard.

Deterministic tooling also helps systemically enforce the established rules where possible. Constitution says to follow test-driven development? Then there better be complete code coverage. To that end, I also created scripts that scan the code base for things like the number of classes on a given element.

I also found that bigger is rarely better when it comes to the model used. For the vast majority of my work, I used Sonnet, only letting the versions increment. I only ever used Opus a few times, when I found Sonnet going in circles on a more complex problem, and that was in the days of the 4.x models. The 5.x model lines haven't really required Opus, and in fact, Opus and Fable have both proven to be far more likely to go off the rails than Sonnet for me.

### What About Collaboration?

(Or...adventures in "brute force" contributions.)

Collaboration is where it gets a little challenging when dealing with non-deterministic tools. For the overwhelming majority of the project, I was the sole engineer, but on the tail end, when the bugs started getting harder to pin down and the feature gaps started getting harder to articulate, my colleague, Gaian, started jumping in on the engineering.

Now, this is fine, of course. Software development is a team sport. However, I expected either he or his Claude Code instance to do more digging to find established norms than they actually did, or to have a similar enough workflow to what I was doing (reference a ticket, plan out execution, implement) that the structural things could be uncovered naturally. I suspect he expected Claude to be better at discovering those things, too.

We were both so very wrong.

Claude, it turns out, does not do a very good job in discovering such things on its own. This was especially the case before the recent update that officially made it follow `AGENTS.md` in addition to `CLAUDE.md`, even though it was in theory supposed to already do that. I tried working around the limitation when it became clear it didn't, by putting in `CLAUDE.md` to go to `AGENTS.md`, but by Claude's own admission later on, it turns out that "not at all" was the answer to whether it *actually* followed that breadcrumb.

After a couple rounds of doing code reviews and finding the documented rules/guidelines were being followed only by happenstance, I dug into *why* that was the case, and found two key issues:

1. Gaian was using Opus, which was working better for his natural workflow that he'd fallen into.
2. He *wasn't* using the skills provided in the project.

Opus (and Fable), in my experience, overengineers everything and is far more prone to the "I fixed this thing you asked me to...and this, this, and this thing that you didn't ask about" thing that frustrates a lot of users. It over "thinks" and overengineers, leading to a lot of brittleness in the app and churn in the code, and that was evident in the code in the pull requests. Not using the provided skills and, thus, the workflows to go with them, Claude tended to go off on wild tangents and make a bunch of changes at once, instead of keeping things more focused.

Things improved in the next round of PRs, after I first noticed that Gaian had been using Opus, and suggested he use Sonnet instead, and requested more focused PRs. However, I was still finding myself having to basically rewrite the submitted code, so it complied with the rules of the project. It turned out that Gaian hadn't been following a close enough workflow, and Claude just...didn't pick anything up.

*That said*...this "I'm going to hack my way to the end result that I'm looking for, toss it into a throwaway branch and PR, and let the Principal rework it for real" process actually...wasn't all that bad. We were working in parallel, so he wasn't blocking me by doing that sort of thing, and it gave me a concrete "point B" to then rework from, as opposed to trying to get him to articulate what he envisioned in a way that I could then translate to code. While I'd prefer regular tickets the old-fashioned way, this method proved useful in prototyping out features or more complex bug fixes to unblock him, while providing me with some insight into what he was going for.

## Adventures in Cross-Platform Development

Remember how I chose Tauri to make multiplatform development easier? Well, it certainly *did*, but there's always *something.*

I like developing for Linux and Mac. At the command line level, it's easy to write for both, because they both play nice with each other. Why? Because both Mac and Linux are [POSIX-compliant](https://www.baeldung.com/linux/posix), largely if not fully. This means things like path formats are the same, even if locations differ, and escape sequences are the same, and the fundamental commands are the same, and environment management is the same.

You know what platform *doesn't* comply with POSIX?

Windows. Because of course it doesn't. Why would it comply with an industry standard as old as itself? Standards!? We don't need standards where we're going! That, of course, means we had to account for things with Windows that we didn't have to account for on the non-Windows side. 

Like how Windows paths aren't case-sensitive...except when they are. As it turns out, CMake on Windows *requires* the drive letter to be capitalized, or it breaks in weird ways. Thankfully, because Opal has some amount of control over how it writes paths, so we could ensure that happened.

What tripped us up a number of times, though, were the slashes, because while it's common knowledge that Windows uses backslashes instead of forward, some interfaces and libraries already handle it, and it wasn't immediately apparent that the ones we were using...weren't among them. This led to some oddball issues where nothing would throw any exceptions, but we'd end up with behaviors like engines registering just fine, but then other engine-finding logic not being able to find them, creating duplicate entries. So that was fun.

## The Joys of Making a Value-Add Product

We intentionally made Opal leverage O3DE as much as possible. Nearly all the interactions with engines and project and gems are done through O3DE's own command line interface. We did this, because there is a lot of "magic" that O3DE does under the hood that would be a pain in the ass to replicate. Besides, that's what the CLI is there for. It's actually the same thing O3DE's own Project Manager does, so this is a well-established method within the ecosystem. As a result, we could piggy-back off the existing manifests and make them the source of truth for all releveant metadata.

*However*, as a third party outsider, approaching from a different paradigm, we ran into a number of quirks.

### Naming Things Is Hard

Name collisions are something I've been concerned with for a while, and have been a surprisingly contentious topic in the O3DE community. I expected potential technical issues with gem names, but surprisingly, it was engine names that gave us the most trouble.

The `engine.json` manifest file provides a name field for the engine to distinguish itself. Official copies of O3DE identify themselves as `o3de` and `o3de-sdk` for the source and SDK builds, respectively. That's all well and good...except when we ran into this issue, the engine registration script would write to an `engines_paths` field, which was keyed by the engine name.

Uniquely.

Oh, and the registration script would fail silently.

This wasn't historically a problem for O3DE, because the tight coupling of the Project Manager to the engine version means it has overriding mechanisms that cover up the issue. Decoupling project management from the engine, however, shines a big ol' spotlight on it. Because Opal keeps an internal cache to avoid excessive file reads and writes, which it updates in certain circumstances, such as startup, this issue resulted in the **Mystery of the Vanishing Engines** -- Opal would register an engine, it would appear in the list as normal, but the manifest wouldn't be written as expected. Then, on the next update from the manifest, the engine would disappear (or, if the user manually force-registered the engine, the *old* engine by that name would disappear).

Related to that, we also had **Shroedinger's Project Engine** -- Opal would change the engine for a project, which would change the `user/project.json` file as expected (...after we learned about that file as an override to what's in the base `project.json` file, which was its own gotcha), but then trying to build would fail, when the engine name in `project.json` didn't match the engine name in the folder `user/project.json` pointed to.

But finding the root cause was one thing, trying to solve it was another. On the one hand, because O3DE is an open-source project, we could submit [an issue to identify the problems](https://github.com/o3de/o3de/issues/19885), and/or [PRs to fix](https://github.com/o3de/o3de/pull/19905) [the problems](https://github.com/o3de/o3de/pull/19903), which we did, but also, a large open source project like O3DE has a relatively long turnaround time. My PRs were merged back in July, but wouldn't find their way into release until the end of October, when 26.10 drops. On the other hand, we could try to work around the problem, but that required renaming engines, which would disrupt version control for those engines (because it had to be done in their `engine.json` files) and we had to come up with convoluted naming schemes for internal Opal reasons.

We tried the name workaround for a while, but eventually gave up on it. What we ultimately settled on was checking if the engine registered, or if the script failed silently, and re-ran the registration with the `--force` flag. We separated out how we generated the display names to use the folders, instead of trying to rely on name in the engine's manifest. Now, when names collide, Opal walks up the ancestor tree until it finds a unique combination, or determines the existing and candidate entries are legitimately duplicates. Since nothing actually uses `engines_path`, aside from the registration and , even prior to 26.10, this turned out to be the most reliable way to handle these. 

There's still the problem of only one of multiple engines with duplicate names winning and being in `engines_path` in the manifest, but the build-time check in the older versions of O3DE only checks against the name in the engine's and project's own manifests, which bypasses the `engines_path` issue altogether, albeit by happenstance.

Sometimes, you just gotta do what works.

### The Current Manifests Are...A Bit of a Mess

O3DE has gone through a couple iterations for its manifest files, and there's currently [an RFC open for Schema 2.0](https://github.com/o3de/rfcs/issues/53) that attempts to standardize the whole thing into something more predictable. It's sparked a fair bit of discussion in the time since its original inception, but I agree with the direction it's going.

The project manifest isn't too bad. It describes the project and provides some pretty bog-standard information. The engine, user, and repo manifests, however, leave much more to be desired, with `o3de-extras`' `repo.json` being by far the worst -- and most reflective of the competing visions for what should be in a manifest and where (especially one whose purpose is to describe other objects in the ecosystem).

The `repo.json` file is [explicitly intended to describe remote gems that can be fetched separately from the engine](https://docs.o3de.org/docs/user-guide/remote-content/remote-repository-overview/), which is great, and pretty well standard practice for this kind of thing...except `o3de-extras`' own file not only doesn't even comply to the Schema 1.0 spec, but isn't even internally consistent.

After trying to figure out what was expected where, I had Claude scan the whole file to see what its current state was. What it found:

- 18/20 gems had their `sha256` at gem level (the spec says it should be in `versions_data`)
- 14/20 had `download_source_uri` at the gem level (again, should be in `versions_data`)
- 7/20 had no `versions_data` at all
- Various gems were missing some combination of `icon_path`, `documentation_url`, and `version`
- Various gems had fields that aren't defined in the spec at all

### Windows Is Just An All-Around PITA

One of the nice things about Linux and Mac is that underneath it all, their installers and applications are typically just archives with some extra scripts to tell the installer where to put the executables (or the application itself is just a self-contained binary and the "installer" is little more than a script that puts it in a standard place for the platform). This means, for example, that I can take the `.deb` file that the O3DE pipeline creates and use it on any Linux system by unarchiving it and doing whatever I want with the contents.

Windows, of course, is the odd one out on this. Again.

Now, there *is* a format that does this same kind of thing (known as a self-extracting archive), but those are somewhat uncommon in consumer software by default. The more common path is a full binary installer, which requires running and letting it put things where *it* wants, write to the registry, and whatever else it's set up to do, even though O3DE doesn't actually need...any of that, really. O3DE's current pipeline doesn't create what's known in the Windows world as a "portable" version, which is the compiled files in an archive. Thankfully, the group in charge of maintaining that pipeline has been open to adding that to the release artifacts (since O3DE *can* be distributed that way, the project just doesn't), which will be nice once it happens.

On top of that, the process of downloading and installing O3DE's Python dependencies still fails on occasion, despite the concerted effort to fix that issue. When it fails, it either aborts and rolls back the installation (older versions) or leaves the engine in a partial state that the internal project manager would then try to remedy. Opal, of course, replaces and therefore bypasses the internal project manager, so we had to replace that functionality, and automatically recover when that happens. Opal, then, puts forth its best effort to fix the issue before alerting the user, since most of the time, it's recoverable unless the user needs to do something specific, like connect to the internet.
